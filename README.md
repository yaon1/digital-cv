# Цифровая визитка: backend на NestJS, Prisma и GraphQL

GraphQL API, который рассказывает о разработчике: профиль, навыки, опыт работы с достижениями и проекты.
Через встроенный Apollo Sandbox можно выполнять запросы прямо в браузере.

Живая версия: https://digital-cv-ig1f.onrender.com/graphql (бесплатный тариф Render, первый запрос после простоя открывается до минуты).

Стек: TypeScript, Node.js 22, NestJS 11, Prisma 6, PostgreSQL 16, GraphQL (Apollo Server 5, code-first), DataLoader, Docker, Git.

## Запуск с нуля

Нужен Docker.

```bash
docker compose up --build
```

Затем открыть http://localhost:3000/graphql, откроется Apollo Sandbox. Миграции применяются и данные заполняются автоматически при старте контейнера.

Запуск без Docker для приложения (нужна PostgreSQL, например `docker compose up db`):

```bash
cp .env.example .env
npm ci
npx prisma migrate deploy
npm run build && npm start     # или npm run start:dev
```

Тесты (нужна запущенная база, `docker compose up -d db`, затем `npx prisma migrate deploy`):

```bash
npm test
```

## Пример запроса

```graphql
query {
  profile {
    name
    title
    description
    links { label url }
    skills(category: "Backend") { name }
    experience {
      company
      position
      period
      achievements { text }
    }
    projects { name url technologies }
  }
}
```

Другие запросы: `profile(slug: "sergey-arinin")` и `profiles` (список). Поле `skills` принимает необязательный фильтр `category`.

## Структура

```
prisma/
  schema.prisma            модель данных
  migrations/              SQL-миграции
src/
  prisma/                  PrismaService (подключение), глобальный модуль
  profile/
    models.ts              GraphQL-типы
    profile.resolver.ts    GraphQL: запросы и поля-связи
    profile.service.ts     бизнес-логика
    profile.repository.ts  все запросы к базе
    profile.loaders.ts     DataLoader'ы на один HTTP-запрос
  seed/
    data.ts                данные визитки
    seed.service.ts        заполнение базы при старте
  app.module.ts            сборка модулей, настройка GraphQL и Apollo Sandbox
test/                      e2e-тесты
```

## Архитектурные решения

**Слои и разделение ответственности.** Резолвер только принимает запрос GraphQL и вызывает сервис, сервис содержит логику (выбор профиля, формат периода работы, 404 для несуществующего профиля), репозиторий единственный знает про Prisma. Благодаря этому GraphQL-слой можно заменить на REST, а базу на другую, не переписывая остальное.

**Вложенные данные и оптимизация запросов.** Профиль со связями можно загрузить через `include`, но тогда база вернёт всё, даже если клиент попросил только имя. Поэтому поля `links`, `skills`, `experience`, `projects` и `achievements` вынесены в `@ResolveField` и загружаются только по требованию. Чтобы это не породило N+1 (по запросу на каждый опыт работы или каждый профиль), каждое такое поле читает данные через DataLoader. Он собирает все обращения за один такт событийного цикла и отправляет один запрос `WHERE parentId IN (...)`. В итоге число SQL-запросов равно числу уровней вложенности в запросе (профиль, навыки, опыт, достижения), а не числу записей. e2e-тест считает SQL-запросы и проверяет это: запрос `{ profile { name } }` делает 1 SELECT, полный запрос всех связей делает 6.

**DataLoader на каждый HTTP-запрос.** Лоадеры создаются в `context` заново для каждого запроса, поэтому кэш не попадает от одного клиента к другому и данные не устаревают.

**Code-first схема.** GraphQL-схема строится из TypeScript-классов, поэтому типы описаны один раз, а схему не нужно вести отдельным файлом. Prisma-типы и GraphQL-типы намеренно разделены: Prisma описывает таблицы, GraphQL описывает то, что видит клиент (например, вычисляемое поле `period`, которого нет в базе).

**Модель данных.** Профиль, ссылки, навыки, опыт, достижения и проекты лежат в отдельных таблицах со связью по `profileId` и индексами на внешних ключах. Достижения вынесены из опыта в отдельную таблицу, чтобы их можно было запрашивать и выводить независимо. Порядок элементов хранится в `position`, даты опыта в `DATE` (конец `NULL` значит «по настоящее время»). Таблица `Profile` допускает несколько профилей, поэтому API принимает `slug`.

**Инициализация и заполнение базы.** Схема создаётся миграциями Prisma (`prisma migrate deploy` выполняется при старте контейнера). Данные заполняет `SeedService` при старте приложения: профиль с тем же `slug` заменяется целиком в одной транзакции. Поэтому запуск с нуля и перезапуск дают одинаковый результат, а чтобы изменить данные визитки, достаточно поправить `src/seed/data.ts` и перезапустить приложение.

**Docker.** Двухэтапный образ: на первом этапе сборка и удаление dev-зависимостей, на втором только то, что нужно для запуска. `docker-compose.yml` ждёт готовности PostgreSQL (healthcheck) перед стартом приложения.

**Apollo Sandbox.** Подключён встроенный плагин Apollo Server, интроспекция включена, поэтому песочница работает и в production-режиме. Встроенный GraphQL Playground из NestJS отключён: Apollo разрешает только один плагин стартовой страницы.

## Что можно улучшить

Авторизация и мутации для редактирования данных не добавлялись: по ТЗ визитка только читает данные. Для публичного развёртывания стоило бы добавить ограничение глубины и сложности запросов (например, `graphql-depth-limit`).
